## Purpose

Define the structured AI student action model, its state machine and
single-execution semantics, the frontend `AIActionRunner` animation framework,
the stable `data-ai-target` identifier contract, cross-page action recovery, and
the clear boundary between animation and real backend operations.

## Requirements

### Requirement: AI generates controlled structured student actions
The system SHALL have the AI produce a controlled structured student action instead
of free-form execution. Each action SHALL be one of the approved action types
(`create_student`, `update_student`, `delete_student`, `search_students`,
`get_student`, `count_students`) and SHALL carry a validated `payload` and, where
applicable, a resolved `target`. The AI SHALL NOT generate JavaScript, arbitrary CSS
selectors, SQL, or script that is executed by the browser.

#### Scenario: Approved action types are the only supported operations
- **WHEN** the AI responds to a student operation request
- **THEN** the resulting action SHALL be one of `create_student`, `update_student`,
  `delete_student`, `search_students`, `get_student`, or `count_students`
- **AND** any operation outside this whitelist SHALL be rejected with a structured
  error and SHALL NOT be executed

#### Scenario: Action payload and target are validated server-side
- **WHEN** the AI produces an action payload or target
- **THEN** the server SHALL validate the payload fields, types, ranges, and the
  uniqueness rules using the same rules as `StudentService`
- **AND** for `update_student` and `delete_student`, the `target` SHALL resolve to a
  unique existing student (by `student_id` or `student_number`)
- **AND** an action that references a non-existent or ambiguous target SHALL be
  rejected without executing any operation

#### Scenario: AI cannot execute arbitrary code or selectors
- **WHEN** the AI requests an operation
- **THEN** the system SHALL NOT evaluate or execute any JavaScript generated by the
  AI (`eval`, `new Function`, or similar)
- **AND** the system SHALL NOT execute arbitrary CSS selectors returned by the AI
- **AND** the system SHALL NOT allow the AI to run arbitrary SQL or access the
  database directly

### Requirement: Backend action JSON is semantic-only and controlled
The action JSON returned by the backend SHALL contain only controlled semantic
actions and student field values. It SHALL NOT contain JavaScript, DOM selectors,
CSS selectors, SQL, URLs, or executable code strings. The frontend SHALL resolve
semantic field names to DOM elements through a fixed local mapping.

#### Scenario: Action JSON contains no executable content
- **WHEN** the backend returns an action JSON to the frontend
- **THEN** the JSON SHALL contain only fields such as `action_id`, `action_type`,
  `target_page`, `payload`, `status`, and `requires_confirmation`
- **AND** it SHALL NOT contain JavaScript source, DOM selectors, CSS selectors, SQL
  statements, URLs, or any string that the frontend could execute directly

#### Scenario: Payload uses semantic student field names only
- **WHEN** the backend returns student data for an animation
- **THEN** the JSON SHALL use semantic field names such as `student_number`, `name`,
  `gender`, `age`, `major`, `year_level`, `score`, `phone`, and `email`
- **AND** the frontend SHALL map those names to `data-ai-target` elements through a
  fixed local mapping
- **AND** the backend SHALL NOT send selectors such as `nth-child`, `#id`, `.class`,
  or `data-ai-target` attribute values

### Requirement: Frontend JSON-driven action controller
The system SHALL provide a vanilla-JavaScript controller that reads the controlled
action JSON, validates the `action_type` against a local whitelist, and plays the
predefined animation for that type.

#### Scenario: Controller validates action_type against a local whitelist
- **WHEN** the controller receives an action JSON
- **THEN** it SHALL validate `action_type` against the local whitelist
  (`create_student`, `update_student`, `delete_student`, `search_students`,
  `get_student`, `count_students`)
- **AND** an unknown `action_type` SHALL be rejected without playing any animation

#### Scenario: Controller navigates and re-fetches by action_id
- **WHEN** an action is initiated on the Dashboard and `target_page` is `/students`
- **THEN** the controller SHALL save the minimal `action_id` reference and navigate
  to `/students`
- **AND** after page load it SHALL re-fetch the action from the backend by
  `action_id` before playing the animation

#### Scenario: Animation never mutates data
- **WHEN** the controller plays an animation
- **THEN** the animation SHALL NOT directly modify the database
- **AND** the animation, the confirmation, and the real execution SHALL share the
  same `action_id`
- **AND** the real write SHALL be executed at most once

#### Scenario: Unknown and missing fields are handled safely
- **WHEN** the controller receives an action JSON with unknown fields or with a
  missing required field (`action_id` or `action_type`)
- **THEN** the controller SHALL reject the action without playing any animation
- **AND** unknown fields SHALL be ignored and SHALL NOT be executed or rendered

#### Scenario: Extra payload fields are ignored by the animation
- **WHEN** the payload contains fields not present in the frontend fixed mapping
- **THEN** the animation SHALL fill only the fields present in the fixed mapping
- **AND** the extra fields SHALL NOT affect the DOM or the executed operation

### Requirement: Structured action model
The system SHALL represent every AI student action with a unified structured model
containing at least `action_id`, `action_type`, `payload`, `target`, `changes`,
`target_page`, `requires_confirmation`, `status`, `created_at`, `expires_at`,
`result`, and `error`.

#### Scenario: Action carries stable identity and metadata
- **WHEN** an AI student action is created
- **THEN** it SHALL have a unique `action_id`
- **AND** it SHALL expose `action_type`, `payload`, `target`, and `target_page`
- **AND** write actions SHALL expose `changes` describing the affected fields or rows
- **AND** it SHALL record `created_at` and `expires_at`

#### Scenario: Write and read actions differ by confirmation requirement
- **WHEN** an action is created
- **THEN** `create_student`, `update_student`, and `delete_student` SHALL have
  `requires_confirmation: true`
- **AND** `search_students`, `get_student`, and `count_students` SHALL have
  `requires_confirmation: false`

#### Scenario: Browser-visible action data is redacted
- **WHEN** an action is returned to the browser
- **THEN** it SHALL NOT contain confirmation tokens, API keys, internal signing keys,
  `SECRET_KEY`, the full system prompt, or full raw student records beyond the
  minimum needed for the animation
- **AND** log records SHALL follow the existing redaction conventions

### Requirement: Action state machine
The system SHALL track each action through a defined lifecycle with legal state
transitions. States SHALL include `pending`, `animating`, `waiting_confirmation`,
`executing`, `succeeded`, `failed`, `cancelled`, and `expired`.

#### Scenario: Write action lifecycle
- **WHEN** a write action is created
- **THEN** it SHALL start in `pending`
- **AND** it SHALL transition `pending` → `animating` → `waiting_confirmation` →
  `executing` → `succeeded` or `failed` in order
- **AND** the action SHALL NOT reach `executing` before the user confirms

#### Scenario: Read action lifecycle
- **WHEN** a read action (`search_students`, `get_student`, `count_students`) is
  created
- **THEN** it SHALL transition `pending` → `animating` → `succeeded` or `failed`
  without a `waiting_confirmation` step

#### Scenario: Terminal states are final
- **WHEN** an action reaches `succeeded`, `failed`, `cancelled`, or `expired`
- **THEN** it SHALL NOT transition to any other state
- **AND** the system SHALL reject any attempt to execute, confirm, or re-animate a
  terminal action

#### Scenario: Illegal transitions are rejected
- **WHEN** the system receives a transition that is not legal for the current state
  (for example confirming a `cancelled`, `expired`, or already `succeeded` action)
- **THEN** it SHALL reject the request with a structured error
- **AND** it SHALL NOT execute any write operation

#### Scenario: Server state is authoritative and client cannot force success
- **WHEN** the frontend finishes playing an animation
- **THEN** the frontend SHALL NOT set the action state to `executing`, `succeeded`,
  `failed`, `cancelled`, or `expired`
- **AND** only the server SHALL advance the action to `succeeded` after the real
  backend operation succeeds
- **AND** the frontend SHALL treat `animating` as a presentation state that never
  gates execution

#### Scenario: Expiry is enforced
- **WHEN** an action remains unconsumed past its `expires_at`
- **THEN** its status SHALL be considered `expired`
- **AND** confirming it SHALL return the existing `ai_confirmation_expired` style
  error without executing

### Requirement: Single-execution semantics
The system SHALL guarantee that each `action_id` executes at most once. Replays,
page refreshes, duplicate confirmation clicks, and network retries SHALL NOT cause
a second execution.

#### Scenario: Confirmed action executes exactly once
- **WHEN** a write action is confirmed
- **THEN** the underlying write SHALL be executed exactly once through the existing
  server-side confirmation path
- **AND** a second confirm for the same `action_id` SHALL be rejected and SHALL NOT
  execute again

#### Scenario: Page refresh does not re-execute
- **WHEN** the user refreshes the page after an action was executed
- **THEN** the system SHALL NOT re-execute the action
- **AND** the frontend SHALL detect the executed state and only refresh the student
  list

#### Scenario: Duplicate confirmation clicks are idempotent
- **WHEN** the user clicks confirm multiple times quickly
- **THEN** at most one write SHALL be executed
- **AND** the additional clicks SHALL be ignored or returned as already-used

#### Scenario: MCP and frontend do not double-execute
- **WHEN** a write action is executed through the server confirmation path
- **THEN** the frontend SHALL NOT submit a second independent write through the
  student REST API
- **AND** the animation SHALL remain visual-only and SHALL NOT itself trigger the
  database write

#### Scenario: Animation, confirmation, and execution share one action_id
- **WHEN** a write action is animated, confirmed, and executed
- **THEN** all three stages SHALL reference the same `action_id`
- **AND** the real write SHALL be executed at most once

### Requirement: Write actions require user confirmation before data changes
The system SHALL NOT modify student data for `create_student`, `update_student`, or
`delete_student` until the user has explicitly confirmed the pending action.

#### Scenario: No write before confirmation
- **WHEN** a write action is created and before the user confirms
- **THEN** the database SHALL NOT change
- **AND** the student list SHALL NOT show the new or modified record

#### Scenario: Confirmation binds the original server-validated arguments
- **WHEN** the user confirms a write action
- **THEN** the server SHALL execute the operation using the arguments bound to the
  action at creation time
- **AND** the server SHALL NOT use any arguments re-submitted by the browser

#### Scenario: User cancel prevents execution
- **WHEN** the user cancels a write action
- **THEN** the action SHALL transition to `cancelled`
- **AND** the server SHALL NOT execute any write for that action even if the token
  remains technically valid

### Requirement: Read actions are executed without confirmation
The system SHALL execute read actions (`search_students`, `get_student`,
`count_students`) without a user confirmation step, because they do not modify data.

#### Scenario: Search is not a guided animation
- **WHEN** the user requests a search through AI
- **THEN** the search SHALL be answered through the existing chat read-only flow
  without playing a guided page animation
- **AND** no confirmation SHALL be required

#### Scenario: Read failure is reported without success animation
- **WHEN** a read action fails (for example a search request errors)
- **THEN** the system SHALL NOT play a success animation
- **AND** it SHALL display the failure result

### Requirement: Frontend AIActionRunner animation framework
The system SHALL provide a vanilla-JavaScript animation controller (`AIActionRunner`)
that plays an ordered sequence of visual steps for a structured action. It SHALL
support element waiting, mouse movement, simulated clicks, character-by-character
field filling, select dropdown choice, current-field highlight, a page mask, step
prompts, and pause, continue, skip, and cancel.

#### Scenario: Runner plays the create-student animation
- **WHEN** a `create_student` action starts
- **THEN** the runner SHALL move the simulated mouse to the `student-add-button`
  element and click it
- **AND** open the create modal through the existing button event
- **AND** wait for the create modal to open
- **AND** focus and fill each field in sequence with visual highlighting
- **AND** fire standard `input` and `change` events when filling fields
- **AND** locate and highlight the `student-submit-button`
- **AND** pause before the submit button and wait for user confirmation

#### Scenario: Unified Action Executor performs the write
- **WHEN** the user confirms a write action
- **THEN** the runner SHALL invoke the unified Action Executor (the server-side
  confirmation path) using the shared `action_id`
- **AND** the server SHALL hold and consume the confirmation token
- **AND** it SHALL NOT submit a separate write through the student REST API
- **AND** the real write SHALL be executed exactly once

#### Scenario: Animation never fires the form submit event
- **WHEN** the runner plays a write animation and highlights the submit button
- **THEN** the runner SHALL NOT dispatch a real `click` or `submit` on the submit
  button
- **AND** the visual press on the submit button SHALL be a CSS-only effect
- **AND** the manual form submit handler SHALL be neutralized during guided mode so
  the animation cannot trigger a second write

#### Scenario: Runner uses async step sequencing with element waiting
- **WHEN** the runner advances between steps
- **THEN** it SHALL await the required DOM element or state before proceeding
- **AND** it SHALL NOT rely on long fixed `setTimeout` chains that cannot observe
  page state

#### Scenario: Runner supports pause, continue, skip, and cancel
- **WHEN** the user pauses the animation
- **THEN** the runner SHALL halt at the current step and resume from the same step
  when continued
- **WHEN** the user skips the animation
- **THEN** the runner SHALL skip the remaining visual steps
- **AND** for write actions the user SHALL still be required to confirm before any
  data changes
- **WHEN** the user cancels
- **THEN** the runner SHALL stop the animation
- **AND** cancel any pending write action without executing it

#### Scenario: Manual user interference is detected
- **WHEN** the user manually closes a modal, edits a field, or changes the page
  during animation playback
- **THEN** the runner SHALL detect the state drift
- **AND** SHALL pause or abort with a safe message instead of continuing a stale
  animation

### Requirement: Stable data-ai-target identifiers
The system SHALL identify animation targets on the student page using stable
`data-ai-target` attributes rather than fragile selectors such as `nth-child`.

#### Scenario: Student page elements carry stable AI identifiers
- **WHEN** the student page renders
- **THEN** the create button, search input, search button, modal, form fields, submit
  button, and cancel button SHALL expose stable `data-ai-target` values (for example
  `student-add-button`, `student-search-input`, `student-form-modal`,
  `student-number-input`, `student-name-input`, `student-submit-button`,
  `student-cancel-button`)

#### Scenario: Fragile selectors are not used for animation targeting
- **WHEN** the animation controller locates a target element
- **THEN** it SHALL use the stable `data-ai-target` attribute
- **AND** it SHALL NOT rely on `nth-child`, DOM traversal by table position, or
  selector strings produced by the AI

#### Scenario: AI identifiers are unique on the page
- **WHEN** the student page renders
- **THEN** each `data-ai-target` value SHALL identify exactly one element
- **AND** a template test SHALL assert uniqueness to detect duplicate identifiers

#### Scenario: Missing target prevents any real write
- **WHEN** a required `data-ai-target` element is missing
- **THEN** the animation SHALL abort with a clear "目标元素不存在" error
- **AND** the system SHALL NOT proceed to confirmation or execute any write

#### Scenario: Missing target is detected early
- **WHEN** a required `data-ai-target` element is missing from the page
- **THEN** the runner SHALL fail with a clear "目标元素不存在" error
- **AND** the system SHALL provide a mechanism (for example a test or a startup
  check) to detect missing or renamed `data-ai-target` identifiers after template
  changes

### Requirement: Cross-page action recovery
The system SHALL support actions initiated on the Dashboard being played on the
`/students` page, and SHALL recover in-progress actions after page navigation or
refresh without re-executing completed operations.

#### Scenario: Action reference survives navigation
- **WHEN** the user navigates from the Dashboard to `/students` while an action is
  in progress
- **THEN** `sessionStorage` SHALL store only the minimal non-sensitive action
  reference (for example `action_id`, `action_type`, `target`, `status`)
- **AND** the full action and its confirmation token SHALL be re-fetched from the
  server by `action_id`

#### Scenario: Tokens and sensitive data are not persisted to sessionStorage
- **WHEN** an action is in progress
- **THEN** the confirmation token, full payload, and complete student records SHALL
  NOT be written to `sessionStorage` or `localStorage`
- **AND** the token SHALL live only in server state and in the in-memory JavaScript
  state of the current tab

#### Scenario: Refresh restores unfinished action state
- **WHEN** the page is refreshed while an action is `pending`, `animating`, or
  `waiting_confirmation`
- **THEN** the frontend SHALL restore the action from the server by `action_id`
- **AND** resume the animation from the appropriate step
- **AND** not start a second instance of the same action

#### Scenario: Executed actions are recognized after refresh
- **WHEN** the page is refreshed after an action was executed
- **THEN** the server SHALL report the action as already executed
- **AND** the frontend SHALL NOT re-execute it
- **AND** it SHALL only refresh the student list

### Requirement: Animation and real-operation boundary
The system SHALL keep animation purely visual. Real data changes SHALL be performed
only by the backend through `StudentService`. Playing an animation SHALL NOT by itself
prove or perform a database operation, and success effects SHALL be shown only after
the backend confirms success.

#### Scenario: StudentService remains the single write entry point
- **WHEN** any write is executed
- **THEN** the data write SHALL pass through `StudentService`
- **AND** AI, MCP, and page operations SHALL NOT maintain independent write logic

#### Scenario: Success animation requires backend success
- **WHEN** the backend returns a failure for a confirmed action
- **THEN** the frontend SHALL display the failure result
- **AND** SHALL NOT play the success highlight or success effect

#### Scenario: Animation never mutates the database directly
- **WHEN** the animation controller plays any action
- **THEN** the animation SHALL NOT issue any database write or student REST API write
- **AND** data changes SHALL occur only through the unified server-side execution
  path

#### Scenario: Guided mode neutralizes the manual form submit
- **WHEN** the AI-guided flow is active on the student page
- **THEN** the existing manual form submit handler SHALL be neutralized so that no
  simulated or accidental submit triggers a student REST API write
- **AND** the write SHALL occur only through the unified Action Executor

#### Scenario: Animation does not replace validation
- **WHEN** an action is animated and played back
- **THEN** the backend SHALL still perform permission checks, parameter validation,
  and duplicate checks
- **AND** the animation SHALL NOT bypass or weaken those checks

### Requirement: Error handling for guided actions
The system SHALL handle guided-action errors in a deterministic way, including
duplicate student numbers, missing targets, ambiguous search results, validation
failures, missing DOM targets, failed modal opens, expired or tampered tokens,
already-executed actions, user cancel, manual modal close, network errors, backend
failures, page refresh, and manual user interference.

#### Scenario: Duplicate student number does not play success
- **WHEN** a `create_student` action encounters a duplicate `student_number` on the
  backend
- **THEN** the system SHALL report the duplicate error
- **AND** SHALL NOT play the success highlight

#### Scenario: Target student missing on update or delete
- **WHEN** an `update_student` or `delete_student` action targets a student that no
  longer exists
- **THEN** the system SHALL report a not-found error
- **AND** SHALL NOT play the success effect

#### Scenario: Ambiguous search results are surfaced
- **WHEN** a search yields multiple students matching the requested name
- **THEN** the results SHALL be displayed with an animation
- **AND** any write that depends on a uniquely identified target SHALL be rejected
  until the user resolves the ambiguity

#### Scenario: Token expiry, tamper, and replay produce structured errors
- **WHEN** a confirmation token is expired, tampered, or already consumed
- **THEN** the system SHALL return the corresponding structured error
- **AND** SHALL NOT execute any write

#### Scenario: Network and backend failures are surfaced
- **WHEN** a network error or backend execution failure occurs
- **THEN** the frontend SHALL show a safe failure message
- **AND** SHALL keep the action in a recoverable `failed` or `pending` state as
  appropriate without auto-retrying writes

#### Scenario: Failed action retry requires a new action
- **WHEN** a write action ends in `failed`
- **THEN** it SHALL be terminal
- **AND** a retry SHALL create a new action with a new `action_id` and a new token

#### Scenario: Network timeout queries status before retry
- **WHEN** a confirmation request times out
- **THEN** the frontend SHALL query the action status before any retry
- **AND** it SHALL NOT blindly re-execute the write
- **AND** if the action already succeeded it SHALL only refresh the list

### Requirement: Guided-action security
The system SHALL preserve the existing security properties for guided actions:
operation whitelist, parameter validation, permission checks, confirmation tokens,
token expiry, anti-tamper, replay protection, log redaction, `request_id`, MCP
stdout/stderr separation, and no full student records in logs.

#### Scenario: All existing guards remain active
- **WHEN** a guided action is processed
- **THEN** permission checks, parameter validation, token expiry, anti-tamper, and
  replay protection SHALL behave exactly as in the non-animated AI Chat flow
- **AND** logs SHALL include `request_id`
- **AND** logs SHALL NOT contain passwords, tokens, cookies, sessions, API keys, or
  complete student records
- **AND** MCP protocol output SHALL remain on stdout while diagnostics use stderr or
  logging
